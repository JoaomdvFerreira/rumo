## A. Architecture boundary evidence

`src/app/`, `src/persistence/`) plus the production build:

- `src/domain/**` imports nothing from `react`, `next`, `src/app`, or
  `src/persistence/react` — framework-independent, confirmed by grep
  returning zero hits and by the existing ESLint `no-restricted-imports`
  domain rule passing under `pnpm lint`.
- `src/content/**` is declarative content composed from the WU002 domain
  schemas plus `zod`, with one deliberate, already-accepted exception:
  `src/content/hash.ts` imports `node:crypto` to compute the deterministic
  `contentHash`. This was part of WU004's original implementation
  (`7899d48`), survived WU004's full Project Overseer review including two
  remediation rounds (`AMEND-010`/`AMEND-011`) without being flagged, and is
  the same Node-dependent hash preparation the frozen contract explicitly
  assigns to "server bootstrap." It is recorded as a **finding** below
  because its file location under `src/content/` (rather than a
  server-only module) is easy to misread as a content-layer violation; the
  production build confirms it never reaches a client chunk (see below).
- `src/app/shell/bootstrap.ts` is a Server Component (no `"use client"`)
  and is the sole aggregation point that triggers `node:crypto`-backed
  hashing/fingerprinting via `canonicalContent`/`contentHash` and
  `buildRevalidationContentIndex`; its own header comment states a Client
  Component must never import it directly.
- `src/app/shell/reconstruct.ts` and all 12 `"use client"`-marked shell
  modules (`AppShell.tsx`, `CandidatePicker.tsx`, `IntentEntry.tsx`,
  `QuestionPanel.tsx`, `RequirementsPanel.tsx`, `RouteView.tsx`,
  `SingleResultConfirmation.tsx`, `SourceDisclosure.tsx`, `StepCard.tsx`,
  `UnsupportedResult.tsx`, `useAppShell.ts`,
  `src/persistence/react/useHydratedSession.ts`) import no `node:crypto`
  or `createHash`, directly or via non-type-only imports of
  `bootstrap.ts`/`hash.ts`.
- No Redux/Zustand/XState, DB/ORM client, auth library, or AI SDK exists
  anywhere under `src/` (grep for `redux|zustand|xstate|prisma|drizzle|
  next-auth|@auth|openai|@anthropic-ai|mongodb|mysql|sqlite|supabase|
  firebase` returns zero hits).
- `package.json` dependencies are exactly: `next`, `react`, `react-dom`,
  `zod` (runtime) and `@axe-core/playwright`, `@playwright/test`,

## B. Product contract evidence

The frozen hierarchy (current situation → relevant questions/facts →
requirements/dependencies → primary action ("Faça isto agora") → parallel
work → waits → completion) is implemented once, in the domain engine, and
only rendered by the shell:

- `src/domain/engine/destination.ts` builds `primaryAction`/
  `parallelActions` only from actionable candidates; waits are only
  considered when no actionable work remains; blocked steps are collected
  into a separate `blocked` list and can never enter the actionable
  candidate pool, so they can never become the primary action or a
  parallel action.
- `src/app/shell/components/RouteView.tsx` renders directly from the
  engine's `DestinationResolution` (`primaryAction`, `parallelActions`,
  `waits`, `blocked`) with no re-sorting, re-filtering, or business-rule
  branching in React; its header comment records this constraint
  explicitly.
- Unsupported search input yields zero candidates: `matchIntents` in
  `src/domain/engine/intent.ts` filters any match below
  `INTENT_ACCEPTANCE_THRESHOLD` (80) before returning candidates.
- Ambiguous input (2+ accepted candidates) requires explicit user
  selection: `shellReducer.ts` routes to a `candidates` phase, and
  `CandidatePicker.tsx` never auto-selects the first candidate.
- A single typed match still requires explicit confirmation before a
  session is created: `shellReducer.ts` only auto-proceeds a lone match
  when it originates from a pre-vetted homepage scenario click
  (`source === 'scenario'`); a typed search with exactly one match routes
  to a `singleResult` confirmation phase and only creates a session once
  the user explicitly proceeds (`SingleResultConfirmation.tsx`,
  `shellReducer.test.ts`).
- Aliases map deterministically to canonical destinations:
  `src/content/intents.ts` declares a fixed `destinationId` per alias,
  validated against real canonical Destination ids at content load
  (`checkIntentCatalog`, enforced in `src/content/index.ts`).
- Explicit facts extracted from aliases (Évora rental municipality,
  existing-gas, keep-number) are never silently overridden: `aggregateFacts`
  in `intent.ts` drops a fact key entirely if two accepted aliases disagree
  rather than guessing, and `src/app/shell/questions.ts` treats any already
  -known fact as answered without ever overwriting it; the fixed
  three-question catalog invents no new canonical facts.
- J01 (Mudar de casa), J02 (Eletricidade e gás), and J03 (Internet numa
  mudança) are all present and wired into `src/content/data/index.ts`,
  alongside the Évora water subjourney.

## C. Persistence / hydration evidence

All eleven WU005/WU007 invariants named in the WU008 packet were checked
against current code and hold:

1. No user state in server-rendered HTML — `buildAppBootstrap` returns
   only canonical content and content-derived fingerprints, never session
   or fact data (`src/app/shell/bootstrap.ts`).
2. Hydration is render-pure — `useHydratedSession`'s `getSnapshot` reads
   only an in-memory variable; all storage I/O runs inside a post-mount
   `useEffect`.
3. Most-recent valid session is selected deterministically —
   `selectMostRecentSession` (`src/app/shell/sessionState.ts`) reduces by
   `updatedAt` with an explicit id tie-break.
4. Persisted progress is fingerprint-aware — `src/persistence/revalidate.ts`
   requires both structural reachability and a fingerprint match
   (`src/persistence/fingerprint.ts`) before trusting a persisted step or
   requirement.
5. Stale/incompatible progress is conservatively discarded — a missing
   root Destination discards the whole session; entries failing
   reachability or fingerprint match are dropped rather than trusted.
6. Post-hydration storage failure is surfaced honestly — `useAppShell.ts`
   tracks write failures and `AppShell.tsx` renders a disclosure banner
   when persistence becomes unavailable after hydration.
7. In-memory usage continues if persistence fails — write failures only
   flip a status flag; the reducer/session state never depends on
   persistence succeeding.
8. Reset attempts stale-state cleanup even after persistence has
   degraded (WU007 finding F5) — the reset path calls storage cleanup
   unconditionally, not gated on prior write-failure state.
9. Late hydration cannot undo prior user interaction or reset (WU007
   finding F6) — `shellReducer.ts`'s `sessionRestored` action is a no-op
   once `hasUserInteracted` is true, and that flag is never cleared once
   set.
10. Raw search text is never persisted — the persisted schema
    (`src/persistence/schema.ts`) only allows canonical id/fingerprint
    pairs and typed `FactSet` values, enforced by `z.strictObject`.
11. Personal facts are never placed in URLs — the app has exactly two
    route files (`page.tsx`, `layout.tsx`), no client-side routing exists
    anywhere in `src/app/**`, and no `router.push`/`searchParams`/URL
    construction referencing fact values was found.

## D. Content / provenance / freshness evidence

`pnpm content:check` passed: 11/11 tests in `src/content/check.test.ts`.

- Destination/Route/Step/Provider/Channel references resolve —
  `checkContentGraph` (`src/content/validate.ts`) enforces dangling-reference
  checks across every entity relation, including a channel-belongs-to-its-
  provider check.
- Alias targets resolve to canonical Destination ids — enforced at content
  load via `checkIntentCatalog`.
- Requirements carry required provenance — `missingSourceVerification` and
  `checkDecisionBearingRequirementProvenance` both fail the check when
  provenance is absent.
- `SourceDefinition` and `SourceVerification` remain separate contracts
  (`src/domain/model/source.ts`), with separate data arrays in
  `src/content/data/sources.ts`.
- High-freshness-risk sources are never silently treated as current —
  `staleHighRiskSource` compares the latest verification's
  `contentFreshness` against `freshnessRisk`, and link health is
  explicitly documented and tested as not proving freshness
  (`validate.test.ts`: "does not treat link health as proof of content
  freshness").
- Provider/Channel/Source relationships are real id references (schema-
  enforced), not free text.
- Official source URLs are exposed when available —
  `src/app/shell/sourceDisclosure.ts` prefers the latest verification's
  `finalUrl`, falling back to the canonical `SourceDefinition.url`, and
  `SourceDisclosure.tsx` renders it independent of provider/channel
  presence.
- Routing `contentHash` is deterministic — `computeContentHash`
  canonicalizes via recursive key-sorting (preserving semantically
  meaningful array order); proven by `hash.test.ts`.
- Alias/copy content stays outside the routing `contentHash` by
  construction — `ContentGraph` (`src/content/graph.ts`) has no alias
  field, and `intents.test.ts` explicitly asserts the content hash is
  unaffected by alias content.

No code path treats HTTP/link availability alone as proof of current
guidance; this is a tested, named constraint (see above).
